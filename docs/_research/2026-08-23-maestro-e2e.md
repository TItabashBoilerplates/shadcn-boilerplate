# Maestro E2E / UI テスト 調査（2026-08-23）

対象: 本リポジトリの `.maestro/` を「ローカル（フルローカルのデバッグ）」と
「リモート（staging / production）」で切り替えられる形に整備するための一次情報調査。

インストール済みバージョン: **Maestro 2.4.0**（`pkgs.maestro` / devenv）。
ドキュメントは <https://docs.maestro.dev> の当該ページ（`.md` 版）を実際に読み、
**CLI の `--help` 実出力と突き合わせて確認**した。

---

## 1. 環境切り替えに使える公式の仕組み（これが本作業の土台）

| # | 仕組み | 出典 | 本リポジトリでの使い方 |
|---|---|---|---|
| 1 | **`-e KEY=VALUE`**（`maestro test` / `cloud` / `record`）でパラメータを注入 | [Parameters and constants](https://docs.maestro.dev/maestro-flows/flow-control-and-logic/parameters-and-constants.md) | プロファイル（local/staging/production）ごとの URL・資格情報を注入する唯一の経路 |
| 2 | **`--config=<file>`** でワークスペース設定を差し替え | [Project configuration](https://docs.maestro.dev/maestro-flows/workspace-management/project-configuration.md) | `config.yaml`（ローカル）と `config.remote.yaml`（リモート）を切り替える |
| 3 | フロー冒頭の **`env:` ブロック**（定数）と **`${VAR \|\| "default"}`** による既定値 | 同上 | 「素の `maestro test <flow>` でもローカル既定値で動く」状態を保つ |
| 4 | **`MAESTRO_` 接頭辞のシェル環境変数は自動で取り込まれる**（CLI のみ。Studio は不可） | 同上 | CI で secrets を渡す際の補助 |
| 5 | **`--include-tags` / `--exclude-tags`**、および config の `includeTags` / `excludeTags` | [Test discovery and tags](https://docs.maestro.dev/maestro-flows/workspace-management/test-discovery-and-tags.md) | `ui` / `e2e` / `mailbox` / `admin` の出し分け |
| 6 | `--platform=web\|ios\|android`、`--headless`、`--screen-size WxH`（Web 限定） | CLI `--help`（2.4.0 実出力） | Web をヘッドレスで回す |
| 7 | `--format=JUNIT\|HTML\|HTML-DETAILED`、`--output`、`--test-output-dir` | 同上 | CI のレポート |

### config.yaml に `env:` は**無い**

`config.yaml` のキーは `flows` / `testOutputDir` / `includeTags` / `excludeTags` /
`executionOrder` / `platform` / （Cloud 専用の）`baselineBranch` / `notifications` のみ。
**環境変数を config に書くことはできない**
（[Workspace configuration](https://docs.maestro.dev/reference/workspace-configuration.md) の一覧、
および docs の `?ask=` 問い合わせで確認）。

→ したがって**環境差分は「`--config` でフローの選抜を切り替え、`-e` で値を注入する」**の
2 段構えにするしかない。本リポジトリの runner (`scripts/e2e/maestro.sh`) はこの形にしている。

## 2. Web テストは `appId:` ではなく **`url:`**

[Web Browsers](https://docs.maestro.dev/get-started/supported-platform/web-browser.md):

> For web tests, you replace the `appId` with a `url`. Behind the scenes, Maestro treats
> the URL as the unique identifier for the application session.

既存の `.maestro/web/**` は `appId: com.example.web` + `launchApp.arguments.url` という
**非公式な形**だった。`url:` に統一した。

- 状態はフロー間で**保持される**。`launchApp: clearState: true`（または `clearState`）で
  origin 単位にクリアできる。→ 各フローの冒頭で必ずクリアする。
- Beta。ブラウザは **Chromium のみ**、ロケールは `en-US` 固定、画面サイズは
  `--screen-size` 以外では変えられない。

### 実測（このサンドボックスで実際に緑にしたもの）

`url: ${BASE_URL}/index.html` のフローに対し `maestro test --headless -e BASE_URL=...` で:

- `launchApp` / `launchApp: clearState: true` … OK
- `assertVisible`（テキスト）… OK
- **`tapOn: { id: "email" }` が DOM の `id` 属性に一致** … OK（Web でも `id` セレクタが使える）
- `openLink: <絶対 URL>` … OK
- `runScript` + `env:` の `${...}` 展開 … OK（スクリプト内で展開後の値を確認）

## 3. **`http` レスポンスは `.status`。`.code` は存在しない**（既存スクリプトのバグ）

[Make HTTP requests](https://docs.maestro.dev/maestro-flows/javascript/make-http-requests.md) と
docs の `?ask=` 回答、および GraalJS 上での `Object.keys(res)` 実測が一致:

```
keys = ["ok", "status", "body", "headers"]
```

- `ok` … 2xx なら true
- `status` … HTTP ステータス（数値）
- `body` … 文字列
- `headers` … オブジェクト

**既存の `.maestro/scripts/*.js` は 4 本とも `response.code !== 200` で判定していた。**
`code` は `undefined` なので条件は常に真になり、**成功したリクエストでも必ず throw する**。
つまりテストユーザー作成・削除・メール取得は**書かれた時点から一度も通っていない**。
`.status` に修正した。

> この種の不具合は lint も型検査も通り、Storybook も CI も緑のままなので、
> 「実際に走らせる」以外に検知手段が無い。

## 4. GraalJS（`jsEngine: graaljs`）の制約

- `fetch` / `async` / `await` / `setTimeout` は無い。HTTP は `http.get/post/put/delete/request`、
  待機はビジーウェイト。
- JSON は `json(response.body)` または `JSON.parse`。
- `output.*` に入れた値がフローの `${output.x}` から読める。
  **値は文字列として扱われる**ので、`assertTrue: ${output.status == 200}` のような
  数値比較に依存しない（実測で false になった）。比較するなら文字列で持つ。
- `runScript` 内で `throw new Error(msg)` すると `maestro.log` にメッセージが出る。
  `console.log` はコンソールに出ないので、**デバッグは throw か debug output を見る**。

## 5. コンテナ / root 実行での Web ドライバの前提（CCR・CI で必要）

Maestro の Web ドライバは Selenium Manager 経由で Chrome / ChromeDriver を解決する。
このサンドボックス（root・コンテナ）では **そのままでは起動しない**。実測した失敗は 2 つ:

1. `Running as root without --no-sandbox is not supported`
   → Maestro は Chrome の起動引数を設定できない（`--no-sandbox` を渡す公式の口が無い。
   [Environment variables](https://docs.maestro.dev/maestro-cli/environment-variables.md) にも無い）。
   → Selenium が管理する chrome バイナリを**同ディレクトリの `chrome-real` に退避し、
   `--no-sandbox --disable-dev-shm-usage` を足すシムに差し替える**ことで解決。
2. `This version of ChromeDriver only supports Chrome version 147 / Current browser version is 152`
   → PATH 上に別バージョンの `chromedriver`（`/opt/node22/bin/chromedriver`）があると
   Selenium Manager がそれを優先し、ダウンロードした Chrome とバージョンが食い違う。
   → **PATH からその 1 本を外す**と Selenium Manager が一致するドライバを取得して解決。

この 2 つを `scripts/e2e/maestro.sh` が自動で面倒を見る（ローカル macOS 等では何もしない）。
これにより **CCR サンドボックスでも `e2e-web` が実際に走る**ようになった
（従来は「Maestro は動かない」前提で Playwright の別ハーネス `e2e/` を持っていた）。

## 6. エージェント向けの公式導線は **Maestro MCP**

[Maestro MCP Server](https://docs.maestro.dev/get-started/maestro-mcp.md) が一次情報。
`maestro mcp` を MCP サーバとして起動し、コーディングエージェントがフローの作成・実行・
デバッグを行える。**`maestro chat`（MaestroGPT）は廃止**され、MCP が後継。

本リポジトリの `.mcp.json` には既に `maestro` エントリがある（`command: maestro, args: [mcp]`）。
`npx skills add` で入れられる「Maestro スキル」は現時点で**すべて第三者製**であり
（`tovimx/maestro-mobile-testing-skill` 等）、mobile-dev-inc 公式のものは存在しない。
`.claude/rules/minimal-implementation.md` §3 の選定基準（メンテ実績・利用実績・ライセンス）を
満たす確証が無いため**採用せず**、リポジトリ固有の運用が書ける自作スキル
`.claude/skills/maestro/` を正本として維持・更新する方針とした。
