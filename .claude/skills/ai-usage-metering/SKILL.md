# AI Usage Metering（トークン使用量・コストの計測と集計）

## このスキルが存在する理由

生成 AI の機能は、**原価が実行のたびに変動する数少ない機能**である。CRUD は何回叩かれても原価がほぼ変わらないが、
LLM 呼び出しは「誰が・どの機能で・どれだけ使ったか」で直接コストが動く。

にもかかわらず、計測は後回しにされやすい。そして**後回しにすると取り返せない**:

- 使用量イベントは**過去に遡って作れない**。計測を入れた日より前の原価は永久に不明のまま。
- 集計軸（`organization_id` など）は**後から列を足しても過去行が NULL**。「テナント別原価を出して」に答えられない。
- 「なぜか今月の請求が 10 倍」の原因調査は、生の usage が残っていないと**不可能**。

だから本スキルの立場はひとつ: **モデルを呼ぶコードを書くことと、使用量イベントを 1 件記録することは、常にセットで実装する。**

---

## 最初にやること（設計の 4 ステップ）

実装に入る前に、この 4 つを必ず決める。決めずに書き始めると、後で作り直しになるのはほぼ集計軸のところ。

### Step 1. 請求主体（billing subject）を決める

「このコストは誰のものか」。ここがすべての集計の起点になる。

| サービス特性 | 主体 | 必須カラム |
|---|---|---|
| 個人向け（1ユーザー = 1契約） | ユーザー | `user_id` |
| 法人向け SaaS / マルチテナント | 組織 | `organization_id` **＋** `user_id`（誰が使ったかの内訳用） |
| API 提供（キー単位で課金） | API キー | `api_key_id` ＋ 発行元の `organization_id` |
| 社内ツール / 未ログインでも使える | なし（機能単位でコスト把握のみ） | `session_id`（匿名でも紐付く識別子） |

**判断のコツ**: 迷ったら「請求書を割る単位」を考える。請求しない社内ツールでも、
「どの機能が高いか」を見るには最低限 `feature` が要る。

> ⚠️ マルチテナントの可能性が少しでもあるなら、**最初から `organization_id` を入れる**。
> 後から足すと過去データが埋まらず、テナント別原価が永久に出せない。これがこの設計で最も高くつく手戻り。

### Step 2. 配賦軸（何に使ったか）を決める

請求主体だけでは「なぜ高いのか」に答えられない。最低限これを持つ:

| 軸 | 用途 | 例 |
|---|---|---|
| `feature` | 機能別原価（どの機能が赤字か） | `chat`, `summarize`, `rag-search`, `image-gen` |
| `trace_id` / `conversation_id` | 1 会話・1 ジョブの総額（エージェントは 1 リクエストで N 回モデルを呼ぶ） | UUID |
| `provider` / `model` | モデル差し替えの効果測定 | `anthropic` / `claude-opus-5` |

**エージェント的な処理では `trace_id` が特に効く。** LangGraph の 1 回の実行は内部で何十回もモデルを呼ぶので、
呼び出し単位のコストだけ見ても「ユーザーの 1 操作がいくらか」が分からない。

### Step 3. 計測単位（unit）を決める

**トークンだけではない。** 生成 AI の課金単位はモダリティごとに違うので、
`quantity` + `unit` の組で持てば同じテーブルに載る。これが「サービス特性によって単位が変わる」への答え。

| モダリティ | よくある課金単位 | `metric` の例 |
|---|---|---|
| テキスト生成 | トークン（入力/出力で単価が違う） | `input_token`, `output_token`, `cache_read_token`, `cache_write_token`, `reasoning_token` |
| 埋め込み | 入力トークン | `input_token` |
| 画像生成 | 枚数 / 解像度 / メガピクセル | `image`, `megapixel` |
| 音声合成 (TTS) | 文字数 or トークン | `character`, `output_token` |
| 音声認識 (STT) | 音声の長さ | `audio_second` |
| 動画生成 / GPU 推論 | 実行秒数 | `compute_second`, `video_second` |
| 外部ツール呼び出し | リクエスト回数 | `web_search_request` |

**設計の含意**: 単価は `metric` ごとに違う。だから「トークン数 × 単価」という 1 本の式ではなく、
**`metric` ごとに (数量 × 単価) を出して合計する**構造にする。詳細は `references/data-model.md`。

### Step 4. 求める精度と即時性を決める（過剰実装を避けるため）

用途によって必要な仕組みが変わる。全部を作る必要はない。

| 用途 | 必要なもの | 不要なもの |
|---|---|---|
| 社内でコストを把握したいだけ | イベント記録 + 日次ロールアップ | 事前見積り、残高チェック |
| ユーザーに使用量を見せる | ＋ RLS 付きの集計ビュー、i18n の単位表示 | 呼び出し前チェック |
| プラン上限を**強制**する | ＋ **呼び出し前**の残高チェック（同期）、超過時のエラー設計 | — |
| 従量課金・クレジット制 | ＋ 冪等な確定処理、プロバイダ請求との月次突合、通貨・端数の規定 | — |

**上限を強制するかどうかが最大の分岐点**。強制するなら「呼ぶ前に残高を見る」経路が要るので、
記録が非同期でよいのか同期で確定させるのかが変わる。ここは必ずユーザーに確認する。

## 実装の骨格

決めた 4 つを、この 3 つの部品に落とす。

```
┌─────────────────────────────────────────────────┐
│ 1. 呼び出しラッパ                                  │
│    モデルを呼ぶ経路を 1 か所に集約し、そこで usage を  │
│    取り出す（呼び出し箇所ごとに書かない = 記録漏れ防止） │
└────────────────────┬────────────────────────────┘
                     │ 生の usage（プロバイダが返した値そのまま）
┌────────────────────▼────────────────────────────┐
│ 2. コスト計算（純関数）                             │
│    usage + 単価表 → metric ごとの金額 → 合計         │
│    副作用ゼロにして単体テストで固める                  │
└────────────────────┬────────────────────────────┘
                     │ 生の usage ＋ 計算結果 ＋ 使った単価表のID
┌────────────────────▼────────────────────────────┐
│ 3. 永続化 + 集計                                   │
│    イベント（生ログ）→ ロールアップ（日次/月次）        │
└─────────────────────────────────────────────────┘
```

### 譲れない 4 つの原則

**1. 最終成果物は「トークン数」ではなく「金額（USD）」。** トークン数だけ記録して満足しない。
入力・出力・キャッシュ読み・キャッシュ書き・reasoning はそれぞれ単価が違い、**モデルが違えば桁が違う**ので、
トークン合計からは金額を復元できない。**すべてのイベントに確定した USD 金額が入っている状態**をゴールにする。

金額が入る経路は 3 つある。どれを使うかを設計時に決める:

| 経路 | 使う場面 | 実装 |
|---|---|---|
| **A. 単価表 × 数量**（既定） | ほぼすべてのプロバイダ | `metric` ごとに (数量 × 単価) を出して合計。`data-model.md` |
| **B. プロバイダが金額を返す** | OpenRouter 等（`cost` / `cost_details.upstream_inference_cost` を常に返す） | **A も併走させて両方保存**。差分が単価表のズレ検知になる |
| **C. 呼び出しに紐づかない従量課金** | プロンプトキャッシュの**保管料**（Gemini は「1M トークンあたり $1.00 / 時間」のように時間課金）、専用スループット等 | 呼び出しイベントでは絶対に捕まらない。**定期ジョブで別イベントとして記録**する |

**C を忘れると「呼び出しコストは全部把握しているのに請求と合わない」**という形で表面化する。
キャッシュを使うなら保管料の有無を必ず料金ページで確認すること。

**2. 生の usage を必ず残す。** 計算後の金額だけ保存すると、単価表が間違っていたときに再計算できない。
プロバイダが返した usage オブジェクトはそのまま `jsonb` に入れておく。ストレージ代よりも、
「請求が合わないが原因が分からない」ほうが遥かに高くつく。

**3. 単価をコードに埋め込まない。** 単価は改定される。`effective_from` 付きの**データ**として持ち、
イベントには「計算に使った単価レコードの ID」を残す。こうしておくと、単価改定後も過去分の再現ができる。
このスキル自身も具体的な金額を書かない（陳腐化するため）。単価は必ず**公式の料金ページを確認**して登録する
（一次情報源の一覧は `references/pricing-sources.md`、`.claude/rules/research.md`）。

> ⚠️ **単価表が空だと、どれだけ丁寧に usage を記録してもドル金額は出ない。**
> モデルを 1 つ足したら、**その場でそのモデルの単価を登録する**までが実装。
> 登録を忘れたイベントは `price_missing` として可視化し、**金額 0 円として集計に混ぜない**
> （0 として扱うと原価が安く見え、しかも誰も気づかない）。

**4. 二重計上を構造で防ぐ。** リトライ、Webhook 再送、ストリーミング再接続で、同じ呼び出しが 2 回記録される。
プロバイダのレスポンス ID（OpenAI の `response.id`、Anthropic の `message.id` 等）を
**一意制約**にして、DB に弾かせる。アプリのロジックで防ごうとすると必ず漏れる。

## 本リポジトリでの配置

`.claude/rules/supabase-first.md` の判断がそのまま適用される。

| 呼び出し場所 | usage の記録先 | 備考 |
|---|---|---|
| Edge Function から短時間の推論 | その関数内で `service_role` クライアントから insert | 外部 API 連携の既定 |
| backend-py（LangChain / LangGraph / 長時間ジョブ） | callback handler で一元記録 | 呼び出し箇所ごとに書かない |
| フロントエンドから直接 | **禁止**。キーもコストも守れない | `.claude/skills/fal/SKILL.md` §1 と同じ理由 |

- テーブルは **Drizzle が source of truth**（`drizzle/schema/`）。`.claude/rules/database.md` に従いマイグレーションは承認制。
- 使用量テーブルは **RLS 必須**。他人・他テナントのコストが見えるのは事故。`.claude/skills/rls/` を参照。
- 記録の失敗を握りつぶさない（`.claude/rules/error-handling.md`）。売上・原価の欠損に直結する。
- コスト計算は純関数なので **TDD 対象**（`.claude/rules/tdd.md`）。UI ではないので Storybook 例外には当たらない。

## よくある誤解

| 誤解 | 実際 |
|---|---|
| 「LangSmith / プロバイダのダッシュボードで見えるから自前計測は不要」 | 外部ツールは**自社のユーザー・組織・機能の軸を知らない**。「どのテナントがいくら使ったか」は自前で持つしかない。外部ツールは突合先としては有用 |
| 「トークン数 × 単価で出る」 | キャッシュ読み/書き・reasoning・バッチ割引で単価が変わる。`metric` ごとに単価が要る（`references/providers.md`） |
| 「合計トークンだけ持てば十分」 | 入力と出力で単価が数倍違う。合算した時点で金額は復元できない |
| 「使用量画面にトークン数を出せば十分」 | **トークン数を見ても高いか安いか判断できない。** 同じ 1 万トークンでもモデルとキャッシュ有無で金額が桁違いになる。画面に出すのは**ドル金額**（トークン数は内訳として） |
| 「単価は実装が終わってから登録すればいい」 | 単価表が空の間のイベントは `price_missing` になる。後から登録＋再計算はできるが、**再計算バッチを作らないと永久に未計上**のまま |
| 「エラーになった呼び出しは記録しなくていい」 | **途中まで生成されていれば課金される**。特にストリーミング中断とツールループ。失敗も記録する |
| 「まず動かして、コスト計測は後で足す」 | 過去のイベントは作れない。**足せないものだけ最初に入れる**（イベント記録と集計軸）。ロールアップや画面は後でよい |
