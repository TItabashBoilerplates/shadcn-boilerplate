# 円換算（USD → JPY）

**大原則: USD を source of truth として保存し、JPY は派生値として扱う。**
プロバイダの請求は USD 建てなので、JPY で保存すると請求突合ができなくなる。

## 結論（用途で使い分ける）

| 用途 | 使うレート | 頻度 | 保存 |
|---|---|---|---|
| **社内ダッシュボード**（速報値） | ECB 参照レート（無料 API・鍵不要） | 日次 | 表示時換算でよい |
| **会計計上・原価確定** | 主たる取引金融機関の **TTM** | **月初固定を継続適用**（後述） | 換算結果を**凍結して保存** |
| **ユーザーへの JPY 請求** | **換算しない**。JPY 建て価格を別途設定する | — | — |

この 3 つを混ぜないこと。速報値と会計値が食い違うのは正常であり、**同じ数字にしようとすると破綻する**。

## 1. 無料で使えるレート API

| | **Frankfurter** | 銀行公表相場（MUFG 系） |
|---|---|---|
| 料金 | 無料 | 無料 |
| API キー | **不要** | —（Web ページ / Excel） |
| データ源 | **ECB 参照レート**（EUR 基準） | MUFG の **TTS / TTM / TTB** |
| 更新 | ECB が毎営業日 16:00 CET 前後に公表 | **11:00 JST 頃**（東京本部の最終公示） |
| 週末・祝日 | **直近営業日の値に自動フォールバック** | 営業日のみ |
| 履歴 | API で日付指定可 | Excel で 1990 年以降 |
| **会計・税務の一次資料として** | **✕**（参照レートであり TTM ではない） | **◎**（「主たる取引金融機関の相場」に該当しうる） |

### Frankfurter（実測）

```bash
# 最新
GET https://api.frankfurter.dev/v1/latest?base=USD&symbols=JPY
→ {"amount":1.0,"base":"USD","date":"2026-08-07","rates":{"JPY":158.34}}

# 日曜（2026-08-02）を要求 → 直近営業日 7/31 の値が返る
GET https://api.frankfurter.dev/v1/2026-08-02?base=USD&symbols=JPY
→ {"amount":1.0,"base":"USD","date":"2026-07-31","rates":{"JPY":160.24}}
```

**要求した日付とレスポンスの `date` は一致しないことがある。**
必ず**レスポンスの `date` を保存する**。要求日で記録すると、「7/31 のレートを 8/2 のものとして記録した」状態になり、
後から検証できなくなる。

**ECB 参照レートの性質**（誤用しないために）:

- **EUR 基準**。USD/JPY は `EUR/JPY ÷ EUR/USD` の**クロスレート**であり、銀行の TTM とは値が違う
- 銀行のスプレッド（TTS/TTB の幅）を含まない**中値の参考値**
- TARGET 休業日は公表されない

→ **社内のコスト把握には十分。会計の一次資料にはしない。**

### 銀行公表相場（会計用）

三菱UFJリサーチ&コンサルティングが MUFG の TTS / TTM / TTB を公開している
（`https://www.murc-kawasesouba.jp/fx/`、11:00 JST 頃更新、1990 年以降の履歴あり）。
**TTM = (TTS + TTB) / 2**。

公式 API ではないので、自動取得するなら取得先の利用条件を確認すること。
**月初固定運用（§2）なら月 1 回の取得で済む**ので、手入力でも回る。これも月次固定を勧める理由のひとつ。

## 2. なぜ「月初固定」が最良か（税務根拠）

日次でレートを引いて 1 件ずつ換算するのは、一見正確だが**割に合わない**:

- API 障害・欠損日の補完・再計算といったハンドリングが全部必要になる
- 得られるのは精度だけで、原価把握の用途では誤差の範囲
- しかも**日次換算が税務上とくに有利というわけでもない**

法人税基本通達 13の2-1-2 は、原則を「取引日の**電信売買相場の仲値（TTM）**」としつつ、
**継続適用を条件に**次を認めている:

| 条件 | 認められるもの |
|---|---|
| 継続適用 | 収益・資産は **TTB**、**費用・負債は TTS**（LLM の利用料は費用なので TTS も選べる） |
| 継続適用（注 2） | **前月末・前週末・当月初・当週初**の相場、**1 か月以内の一定期間の平均値** |
| 注 1 | 相場は原則「その法人の**主たる取引金融機関**のもの」。ただし**同一の方法により入手した合理的なものを継続使用**していれば認められる |

**つまり「前月末の TTM を当月の全取引に適用する」運用が、通達上そのまま認められている。**
実装は「月に 1 回レートを 1 行入れる」だけになり、日次取得の失敗ハンドリングが丸ごと不要になる。

> **鍵は「継続適用」**。一度決めた方式を、都合よく切り替えないこと。
> 「今月は円安だから日次にしよう」は継続適用に反する。**コードに埋める前に方式を決め、変えない。**

### 推奨する二段構え

```
表示用（速報）… ECB 参照レート・日次   → ダッシュボードのドル/円併記に使う。確定値ではない
会計用（確定）… 銀行 TTM・月初固定     → 月次で凍結。以後は動かさない
```

速報値には「概算」と明示する。確定値と一致しないのは仕様であって、バグではない。

## 3. 実装

### レート表

```typescript
export const fxRates = pgTable(
  'fx_rates',
  {
    id: uuid('id').primaryKey().defaultRandom(),
    baseCurrency: text('base_currency').notNull(),      // 'USD'
    quoteCurrency: text('quote_currency').notNull(),    // 'JPY'
    /** 1 base あたりの quote。USD→JPY なら 158.34 */
    rate: numeric('rate', { precision: 20, scale: 8 }).notNull(),
    /** 'ttm' | 'tts' | 'ttb' | 'ecb_ref' — 会計用と速報用を混ぜないための区別 */
    rateType: text('rate_type').notNull(),
    /** レートが成立した日。API のレスポンスが返した日付をそのまま入れる（要求日ではない） */
    rateDate: date('rate_date').notNull(),
    source: text('source').notNull(),                   // 'ecb/frankfurter' | 'mufg'
    sourceUrl: text('source_url'),
    fetchedAt: timestamp('fetched_at', { withTimezone: true, precision: 3 }).notNull().defaultNow(),
  },
  (t) => [
    uniqueIndex('fx_rates_unique').on(t.baseCurrency, t.quoteCurrency, t.rateType, t.rateDate, t.source),
  ],
).enableRLS()
```

`rateType` と `source` を分けて持つのが要点。**速報値（`ecb_ref`）と会計値（`ttm`）が同じテーブルに同居できて、
かつ取り違えない**。

### 換算結果は凍結する

```typescript
// ロールアップ（または請求確定時）に持たせる
jpyAmount: numeric('jpy_amount', { precision: 20, scale: 0 }),   // 円は整数
fxRateId: uuid('fx_rate_id').references(() => fxRates.id),
```

**なぜ凍結するか**: 表示のたびに換算すると、**先月の金額が今日のレートで変わる**。
会計と噛み合わないし、ユーザーに見せている場合は「昨日と数字が違う」というクレームになる。
確定したら動かさない。

速報表示だけなら凍結不要（毎回計算でよい）。**確定値と速報値でカラムを分ける**のが安全。

## 4. 丸め

- **円の最小単位は 1 円**（小数を持たない。Stripe でも JPY は zero-decimal で `amount: 500` = ¥500。
  他通貨の癖で 100 倍すると 100 倍請求になる — 実装事故が多い箇所）
- **丸めるのは最後の 1 回だけ。** イベント 1 件ごとに円へ丸めてから合計すると、
  1 件あたり 1 円未満の誤差が件数分だけ積み上がる（数万件なら無視できない額になる）
  → **USD で合計してから、最後に円へ丸める**
- 内訳を円で表示する画面では、**内訳の合計 ≠ 総額**になる。これは正しい挙動なので、
  総額は総額として別計算し、必要なら注記する
- 切り捨て / 四捨五入は**決めて固定**する（社内原価なら切り上げ寄りが保守的）。
  これも継続適用の対象と考えて、気分で変えない

## 5. ユーザーに JPY で請求する場合

**USD 原価 × レートで売価を都度作らない。** レートが動くたびに表示価格が変わり、
ユーザー体験としても会計としても破綻する。

- **JPY 建ての価格を明示的に用意する**（Stripe なら manual currency prices で JPY の price を作る）
- 原価（USD）と売価（JPY）は**別々に管理**し、為替変動は**マージンで吸収**する。
  マージンが薄くなってきたら価格改定を検討する、という運用にする
- 「原価に対して今どれくらいマージンが残っているか」を見るために、
  §1 の速報レートで**原価だけを円換算して並べて見る**のは有用。売価をそれで決めないだけ

## 6. 税務上の確認事項（税理士へ）

**コードに埋める前に決める**こと。継続適用が条件なので、後から変えると説明が必要になる。

- [ ] どの金融機関の相場を使うか（**主たる取引金融機関**が原則）
- [ ] **TTM / TTS のどちらを継続適用するか**（LLM 利用料は費用なので TTS も選択可）
- [ ] **月初固定 / 日次のどちらを継続適用するか**（前月末・当月初・月中平均なども可）
- [ ] 円未満の丸め方
- [ ] **海外プロバイダへの支払いにおける消費税の取扱い** — 国外事業者からの
      「電気通信利用役務の提供」に該当し、**リバースチャージ方式**の論点がある。
      申告対象は一般課税かつ課税売上割合 95% 未満の事業者に限られるなど条件があるため、
      **該当有無は必ず税理士に確認する**（本スキルは判断しない）

> ⚠️ ここに書いたのは**制度の枠組み**であり、個別の税務判断ではない。
> 事業者ごとに結論が変わるので、**このスキルの記述を根拠に処理を確定させない**。
