# 単価の入れ方（ドル金額を出すための土台）

**トークン数だけ記録しても金額は出ない。** 単価表が空のままだと、どれだけ丁寧に usage を集めても
「何トークン使ったか」しか分からない。このファイルは**単価を正しく登録するための手順**。

## 1. 公式料金ページ（一次情報源）

**金額は必ずここで確認する。** 記憶・ブログ記事・このスキルの例示から写さない（`.claude/rules/research.md`）。

| プロバイダ | 料金ページ |
|---|---|
| OpenAI | https://openai.com/api/pricing/ |
| Anthropic | https://platform.claude.com/docs/en/about-claude/pricing |
| Google Gemini | https://ai.google.dev/gemini-api/docs/pricing |
| fal.ai | https://fal.ai/pricing （モデルごとのページにも記載） |
| OpenRouter | https://openrouter.ai/models （API でモデル別単価を取得可能） |

**確認する項目**（モデルごとに全部見る。1 つでも欠けると金額がズレる）:

- 入力単価 / 出力単価
- **キャッシュ読み込み単価**、**キャッシュ書き込み単価**（TTL 別に分かれることがある）
- reasoning / thinking トークンの扱い（多くは出力と同単価だが、**別立てのモデルもある**）
- **バッチ実行の割引**（同じモデルでも実行モードで単価が違う → 単価表の `mode` で分ける）
- 長コンテキスト時の単価変動（一定トークン数を超えると単価が上がるモデルがある）
- **保管料・時間課金の有無**（§5）

## 2. 換算: 「$X per 1M tokens」→ 1 単位あたり単価

料金ページはほぼすべて **100万トークンあたり（per 1M / per MTok）** で表記されている。
単価表には **1 トークンあたり**で入れる（`data-model.md` の `unit_price`）。

```
unit_price = 表示価格 / 1_000_000
```

**この割り算を登録時に済ませるのが重要。** 「表示価格のまま入れて、計算時に割る」構造にすると、
プロバイダによって表記単位が違う（1M / 1K / 1枚 / 1秒）ため、必ずどこかで換算を間違える。
**単価表に入る値は常に「1 単位あたりの USD」**という不変条件を守る。

| 表記 | 単位 | `unit_price` |
|---|---|---|
| $3.00 / 1M tokens | 1 トークン | `0.000003` |
| $0.30 / 1M tokens（キャッシュ読み） | 1 トークン | `0.0000003` |
| $15.00 / 1M tokens（出力） | 1 トークン | `0.000015` |
| $0.04 / image | 1 枚 | `0.04` |
| $0.006 / minute（音声） | 1 **秒** | `0.0001` ← **metric の単位に合わせて換算する** |

最後の行が事故りやすい。`metric = audio_second` なら**分単価を 60 で割って秒単価にする**。
metric の単位と単価の単位を一致させること。

## 3. 登録すべき metric の洗い出し

モデルを 1 つ追加したら、**そのモデルで発生しうる metric をすべて登録する**。
1 つでも欠けると、その分のコストが `price_missing` になって集計から落ちる。

テキスト LLM の最小セット:

```
input_token
output_token
cache_read_token        （プロンプトキャッシュを使うなら）
cache_write_5m_token    （Anthropic のように TTL で単価が分かれるなら TTL ごとに）
cache_write_1h_token
reasoning_token         （出力と別単価のモデルのみ。同単価なら output_token に含めて計上）
```

**`reasoning_token` を別 metric にするかは、料金ページ次第。**
出力と同単価なら別立てせず `output_token` として計上する（`providers.md` のとおり
reasoning は多くのプロバイダで `output_tokens` の内数なので、別立てすると二重計上になる）。
別単価のモデルだけ、出力から差し引いて別 metric にする。

## 4. 計算のワークスルー例

単価表に以下が登録されている前提（金額は**説明用の仮の値**。実際は §1 で確認する）:

| metric | unit_price (USD/単位) |
|---|---|
| `input_token` | 0.000003 |
| `cache_read_token` | 0.0000003 |
| `output_token` | 0.000015 |

Anthropic のレスポンスがこう返ってきたとする:

```json
"usage": {
  "input_tokens": 500,
  "cache_read_input_tokens": 12000,
  "cache_creation_input_tokens": 0,
  "output_tokens": 800
}
```

**正規化**（Anthropic は外数なので、そのまま metric に対応する。`providers.md` §1）:

| metric | quantity | unit_price | cost |
|---|---|---|---|
| `input_token` | 500 | 0.000003 | 0.001500 |
| `cache_read_token` | 12,000 | 0.0000003 | 0.003600 |
| `output_token` | 800 | 0.000015 | 0.012000 |
| **合計** | | | **$0.0171** |

**ここで確認できること**: キャッシュを使わなければ入力 12,500 トークンが `input_token` 単価で
$0.0375 になっていた。**トークン数は同じでも金額は 2 倍以上違う。**
これが「トークン数だけ見ても原価は分からない」ということの実例であり、
metric ごとに単価を持つ設計が要る理由。

`total_cost = 0.0171` をイベントに保存し、内訳 3 行を `ai_usage_items` に保存する。

## 5. 呼び出しに紐づかないコスト

**呼び出しイベントだけでは絶対に捕まらない課金**がある。ここが抜けると
「呼び出しコストは全部把握しているのに請求額と合わない」になる。

| 種類 | 例 | 記録方法 |
|---|---|---|
| **キャッシュ保管料** | Gemini の明示的キャッシュは「1M トークンあたり $1.00 / 時間」のような**時間課金**がある | 定期ジョブで「保管中のトークン数 × 経過時間」を `metric = cache_storage_token_hour` として記録 |
| ベクトルストア / ファイル保管 | アップロードしたファイルの保管 | 同上（日次） |
| 専用スループット / 予約枠 | プロビジョンド容量 | 固定費として月次で 1 イベント |
| 埋め込みインデックスの再構築 | バッチ処理 | ジョブ完了時に記録 |

**判断のコツ**: 料金ページに「per hour」「per day」「per GB-month」という表記があれば、
それは呼び出しイベントでは捕まらない。**必ず別の記録経路が要る。**

## 6. 単価が未登録のときの扱い

新しいモデルを試したとき、単価登録を忘れるのは**必ず起きる**。設計で受け止める:

```
単価が引けない → cost を NULL にし、status を 'price_missing' にする
              → 集計では「未計上」として件数と数量を別枠で表示する
              → 0 として合計に混ぜない
```

**0 として記録するのが最悪**。原価が安く見えるうえ、数字が出ているので誰も異常に気づかない。
NULL にしておけば、集計画面に「未計上 N 件」が出て気づける。

単価を後から登録したら、**`price_missing` のイベントを再計算するバッチ**を流せば埋まる
（生の usage を保存してあるから復元できる。これが原則 2 の効き所）。

## 7. 棚卸し運用

- **モデル追加時**: 単価登録までが 1 セット。単価が入っていないモデルを本番に出さない
- **定期確認**: 料金改定は予告なく入る。月次のプロバイダ請求突合（`implementation.md` §7）で
  乖離が出たら、まず単価表の古さを疑う
- **改定時**: 既存行を UPDATE せず、`effective_to` を入れて閉じ、新しい行を INSERT する。
  過去の請求額が動かないようにするため
- **`source_url` を必ず入れる**: 根拠が消えると、乖離時に何を確認すればいいか分からなくなる
