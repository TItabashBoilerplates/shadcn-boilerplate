# 設計前調査ポリシー（Design-Time Research & Deviation Confirmation）

**CRITICAL / NON-NEGOTIABLE**: **設計を書き始める前に、その設計で使うツール・API・パッケージ・
サービスの一次情報（公式ドキュメント / Context7 / 型定義）を、実際に読んで理解すること。**
あわせて、**採用するデザインパターン・アーキテクチャ・DB 設計についても、世の中のベストプラクティスを
調査したうえで**設計する。**該当する Skill があれば必ず先に起動する**（`.claude/rules/skills-first.md`）。

そして、**調査結果と食い違う設計書・指示・既存実装を見つけたら、勝手に直しても勝手に従っても
ならない。「意図的な逸脱なのか、単なるミスなのか」を必ずユーザーに確認する。**

> `.claude/rules/research.md` は「**実装**前に一次情報を確認する」ポリシー。
> 本ルールはその 1 段上流、「**設計**の前に理解し、設計書との乖離を確認する」ためのポリシーである。
> 両方が適用される（本ルールが先に効く）。

---

## 0. なぜ設計フェーズで強制するか

**設計の誤りは、実装の誤りより桁違いに高くつく。** 実装ミスは直せばよいが、設計ミスは
**すでに動いているデータと外部契約を巻き込む**ため、後から直せないものがある。

| 後から直せないもの | 何が起きるか |
|---|---|
| DB の集計軸（`organization_id` 等） | 列を後から足しても**過去行は埋まらない**（`.claude/skills/ai-usage-metering/`） |
| 主キー戦略・テーブル分割・テナント境界 | 全行の移行と全クエリの書き換えが必要になる |
| 公開した API / イベントのスキーマ | 利用者がいる以上、壊せない（後方互換の負債になる） |
| 認証方式 | OTP のみで作ると既存ユーザーがパスワードを持たない（`.claude/rules/auth.md`） |
| URL 設計（ページング・ロケール） | 共有リンクと SEO を捨てることになる（`.claude/rules/list-pagination.md`） |
| 価格・単価表・円換算方式 | 会計は継続適用が条件で、遡って変えられない |
| Storage のパス設計 | 既存オブジェクトの移動と署名 URL の作り直しが必要 |

さらに悪いことに、**間違った設計でも実装は完走できる**。ビルドも型チェックも lint もテストも通り、
画面も動く。壊れていることが分かるのは、データが増えたとき・課金が来たとき・審査で落ちたとき・
外部 API の仕様に当たったときである。**だから設計の入口で止める。**

## 1. 発動条件（この作業をするなら本ルールが効く）

以下のいずれかに該当したら、**コードを 1 行も書く前に**§2 の手順を実行する。

| # | 場面 |
|---|---|
| 1 | ユーザーから**設計書・仕様書・要件定義**（Markdown / Notion / 画像 / 口頭）を受け取った |
| 2 | 新機能・新画面・新テーブル・新エンドポイント・新ジョブを**設計する**よう求められた |
| 3 | 外部サービス（Stripe / Resend / OneSignal / LiveKit / fal / Supabase / Vercel / EAS 等）を**新規に組み込む** |
| 4 | 新しいライブラリ・フレームワーク・CLI を**採用する**、またはメジャーバージョンを上げる |
| 5 | **DB スキーマ・RLS・インデックス・マイグレーション**を設計・変更する |
| 6 | 既存設計を**変更する**（テーブル追加、API の破壊的変更、認証方式の変更、料金体系の変更） |
| 7 | アーキテクチャ上の判断をする（どのレイヤーに置くか、Edge Functions か backend-py か、状態をどこに持つか） |

「小さい変更だから」は免除理由にならない。**免除されるのは、既存の設計どおりに書くだけの実装
（新しい API も新しいテーブルも新しい依存も増えないもの）だけ**である。

## 2. 設計フェーズの必須手順

### Phase 0 — Skill を先に起動する（MANDATORY）

`.claude/rules/skills-first.md` に従い、**該当 Skill をすべて洗い出し、最初に起動する**。
Skill は公式ベストプラクティスの取り込み口であり、**Skill を読まずに行った設計はやり直し**になる。

設計フェーズで特に見落とされやすい対応表（正本はセッション冒頭の available skills）:

| 設計する対象 | 先に起動する Skill |
|---|---|
| DB スキーマ・クエリ・インデックス | `supabase-postgres-best-practices`（Postgres 性能ルール）+ `drizzle` + `rls` |
| 行レベル権限 | `rls`（`(SELECT auth.uid())` ラッパー・TO ロール・index・EXPLAIN 検証） |
| フロントのコード配置・依存方向 | `fsd` + `feature-sliced-design`（公式 v2.1） |
| パッケージ / アプリの追加・共通化 | `monorepo` + `turborepo` |
| Python サービス・パッケージの追加 | `python-monorepo` + `fastapi` |
| 画面・UI の設計 | `ui-ux-pro-max`（起点）→ `frontend-design` / `shadcn` / `gluestack` / `mobile-uiux` |
| LLM・生成 AI を使う機能 | `ai-usage-metering`（集計軸は後から足せない）+ `langchain` / `fal` |
| 認証・アカウント導線 | `.claude/rules/auth.md` + `supabase` |
| 一覧・フィード | `.claude/rules/list-pagination.md` + `tanstack-query` |
| 外部サービス連携 | 各サービスの Skill（`stripe-*` / `resend` / `revenuecat` / `onesignal` / `livekit` / `sentry-*` …） |

**該当 Skill が無いと判断した場合は、その旨を設計書に 1 行残す**（探さなかったのか、無かったのかを
後から区別できるようにする）。`find-skills` / `SuggestSkills` で探してから結論を出すこと。

### Phase 1 — 使うものの一次情報を、実際に読む

**「知っている」で飛ばさない。** 設計に登場するすべてのツール・API・パッケージについて、
以下を**この順で**行う。

1. **バージョンを先に確定する**（ドキュメントはバージョンごとに違う）

   ```bash
   cat frontend/package.json frontend/apps/*/package.json   # 実際に入っている版
   bun info <pkg>            # registry のメタデータ（最新版・依存・リポジトリ）
   bun outdated / bun why <pkg>
   uv tree                   # Python 側
   cat supabase/functions/deno.json   # Deno / npm: 指定
   ```

2. **Context7 MCP で、そのバージョンのドキュメントを引く**

   ```
   mcp__context7__resolve-library-id   # libraryName + query → /org/project を得る
   mcp__context7__query-docs           # libraryId（/org/project または /org/project/version）+ query
   ```

   - **`resolve-library-id` を先に呼ぶ**（ユーザーが `/org/project` を明示した場合を除く）。
   - **`query` は 1 呼び出し 1 トピックに絞る**（「routing と auth と caching」のような
     まとめ聞きは精度が落ちる）。トピックが複数あるなら**呼び分ける**。
   - **同一の問いに対して 3 回まで**（ツール側の制約）。足りなければ WebFetch / WebSearch に切り替える。
   - ⚠️ 本リポジトリで有効なツール名は **`query-docs`**。`get-library-docs` は**存在しない**。

3. **Supabase は `mcp__supabase__search_docs`** で公式ドキュメントを引く（インフラの調査・操作自体は
   `.claude/rules/mcp-supabase.md` のとおり MCP 経由）。

4. **Context7 に載っていない / 情報が薄い場合は WebFetch で公式サイトを直接読む**。
   WebSearch は**入口として使い、必ず一次情報に着地させる**（ブログ記事を根拠にしない）。

5. **型定義・スキーマを実物で確認する**（`node_modules/<pkg>/dist/*.d.ts`、`uv run python -c "import ..."`、
   OpenAPI スキーマ、`supabase gen types` の出力）。ドキュメントと実装がズレていることは普通にある。

**この Phase で必ず埋める項目**:

| 項目 | 埋めないと起きること |
|---|---|
| API シグネチャ・必須パラメータ・戻り値の形 | 実装時に総取り替えになる |
| 設定ファイルの形式・キー名・既定値 | 「書いたのに効かない」（本リポジトリで頻発している事故） |
| **非推奨 / 破壊的変更 / 移行手順** | 採用した瞬間に負債になる |
| **制限値・クォータ・レート制限**（サイズ上限・同時実行・タイムアウト・保持期間） | 設計が成立しない（例: Storage の変換は 1〜2500px、`quality` 20〜100） |
| **料金体系と課金単位** | 想定外のコストが出る（例: 画像変換の課金は origin 画像数） |
| **前提プラン・前提設定**（Pro Plan 必須、Dashboard の有効化、ローカルの config） | 本番だけ / ローカルだけ動かない |
| ライセンス | 商用不可が後から判明する（`.claude/rules/minimal-implementation.md` §3） |
| 認証・権限モデル（どの鍵をどこで使えるか） | 秘密鍵がクライアントに出る |

### Phase 2 — デザインパターンと DB 設計のベストプラクティスを調査する

**「一般論として知っているパターン」を当てはめるのは禁止。** パターンにも DB 設計にも
公式・標準の一次情報があり、まずそれを読む。

**アーキテクチャ / デザインパターン**:

- 配置とレイヤー: `feature-sliced-design`（公式 v2.1。レイヤー・公開 API・`@x`）/ `fsd` / `monorepo`
- バックエンドの置き場: `.claude/rules/supabase-first.md` の判断順
  （**supabase-js → Edge Functions → backend-py**。backend-py は LLM / エージェント / 長時間 / 複雑実装のみ）
- 作るか買うか: `.claude/rules/minimal-implementation.md`
  （既存資産 → 標準機能 → マネージド → 実績ある OSS → スクラッチ）
- **フレームワークが用意した「推奨の道」を外れるほど自前コードが増える**。
  Next.js / React / Expo / FastAPI については、その版の公式が推奨する構成を確認してから決める。

**DB 設計**（`supabase-postgres-best-practices` / `rls` / `drizzle` を起動したうえで、最低限これを設計する）:

| 論点 | 決めること・確認すること |
|---|---|
| 正規化 / 非正規化 | 非正規化するなら**理由と更新経路**（トリガ / 生成列 / アプリ）を書く |
| 主キー | 型と生成方法（連番の露出可否、UUID の種別と index への影響） |
| 制約 | `NOT NULL` / `UNIQUE` / `CHECK` / 外部キーと `ON DELETE` の挙動を**DB 側**に置く（アプリの `if` で代替しない） |
| 日時 | **`timestamptz`（`withTimezone: true`）で UTC 保存**（`.claude/rules/datetime.md`） |
| **RLS** | **テーブルを作るなら同時にポリシーを設計**する。ポリシー式に使う列の index、`(SELECT auth.uid())` ラッパー、PERMISSIVE / RESTRICTIVE（`.claude/skills/rls/`） |
| index | クエリパターンから決める。**ページングのソートキー（＋テナント列）に複合 index**（`.claude/rules/list-pagination.md`） |
| ページング | offset か keyset か。**一意列の tiebreaker** を含む決定的な並び順 |
| 削除 | 物理削除 / 論理削除、カスケードの範囲（`on delete cascade` で消し漏れを防ぐ） |
| マルチテナント | 境界列を**最初から**入れる（後から埋められない） |
| 監査・計測 | `created_at` / `updated_at`、使用量イベント（`ai-usage-metering`）、一意制約による二重計上防止 |
| マイグレーション | **Drizzle が source of truth**（`.claude/rules/auto-generated.md` / `database.md`） |

### Phase 3 — 設計書・指示・既存実装と突合する（§3 へ）

調査で分かった事実と、手元の設計書・ユーザーの指示・既存コードを**1 行ずつ突き合わせる**。
乖離が出たら §3 のプロトコルへ。

### Phase 4 — 根拠を残す

- **調査結果は `docs/_research/YYYY-MM-DD-<topic>.md`** に残す（`spec` サブエージェントの出力先と同じ）。
  同じ調査を次のセッションが繰り返さないためであり、**判断の根拠を後から検証できるようにするため**でもある。
- **設計書は `docs/designs/`** に置く。設計書には「**どの選択肢を、なぜ選んだか**」と
  **参照した一次情報の URL とバージョン**を必ず書く。
- 公式の推奨から**あえて逸脱する場合は、理由と根拠を設計書（またはコード comment / PR 説明）に残す**。

## 3. 乖離が見つかったときのプロトコル（本ルールの中核）

**乖離を自分の判断で解消してはならない。** 黙って設計書に合わせるのも、黙って設計書を無視するのも
どちらも禁止。**「意図的なのか、ミスなのか」はユーザーにしか分からない。**

### 3.1 乖離の 4 類型（すべて確認対象）

| 類型 | 内容 | 例 |
|---|---|---|
| **A. 設計書 × 一次情報** | 公式仕様上**実現できない / 非推奨 / 制限を超える** | 「署名 URL を発行した後に画像サイズを変える」（transform は署名時に固定される）、「`SUPABASE_` の環境変数を Doppler に登録」（sync が落ちる） |
| **B. 設計書 × ベストプラクティス** | 動くが、既知の落とし穴を踏む | ページングに tiebreaker が無い、RLS ポリシー列に index が無い、`timestamp`（without timezone） |
| **C. 設計書 × 本リポジトリのルール／既存実装** | `.claude/rules/` や既存の技術選定と矛盾する | モバイルのログインが OTP のみ、一覧が全件取得、UI 文言がハードコード、採用済み領域への重複ライブラリ |
| **D. 実装・既存コード × 設計書** | 設計書に**書かれていない実装**、または**書かれているのに無い実装** | 設計書に無いテーブル列がある、設計書にある画面が実装されていない、命名が設計書と違う |

**D は「実装が古いのか、設計書が古いのか」が外からは分からない**。これも必ず確認する。

### 3.2 確認するときのフォーマット

`AskUserQuestion`（または通常の応答）で、**次の 5 点をすべて含めて**提示する。
「〜のようです、どうしますか？」だけの曖昧な問いは禁止。

```
1. 該当箇所 : 設計書のどこ（節・行）／どのファイル・どの列
2. 事実     : 一次情報で確認した内容（何が / どう違うか）
3. 出典     : URL とバージョン、または Skill / ルールのパス
4. 影響     : このまま進めた場合に何が起きるか（いつ・どう壊れるか）
5. 選択肢   : ① 設計書どおり（意図的な逸脱として進める / 逸脱の理由を記録）
              ② 調査結果に合わせて設計書を修正する（推奨案を具体的に示す）
              ③ 第三の案（あれば）
   + 推奨と、その理由
```

**必ず「これは意図的な選択ですか、それとも記載ミスですか？」を明示的に聞く。**
意図的だと回答された場合は、**その判断をユーザーの決定として受け入れ、理由を設計書に記録して
そのまま進める**（同じ指摘を繰り返さない）。

### 3.3 止めるか、進めるかの基準

| 乖離の性質 | 対応 |
|---|---|
| **後戻りできない**（§0 の表: DB スキーマ・集計軸・API 契約・認証方式・課金 / 単価・URL 設計・テナント境界・Storage パス） | **必ず止めて確認**。回答が来るまでその部分は着手しない |
| **セキュリティ / 権限 / 個人情報 / 決済に関わる** | **必ず止めて確認** |
| **ストア審査・法務要件に関わる**（`.claude/rules/store-review.md` / `auth.md`） | **必ず止めて確認** |
| ローカルで巻き戻せる（命名・ファイル配置・UI の細部） | **仮定を明記して進め**、まとめて報告する |

**止めるときも、他の独立した部分は進める**。全体を止めて回答待ちにするのは、
「どの仮定を置いても危険 / 無駄になる」場合だけ。

### 3.4 やってはいけない解消の仕方

```
❌ 設計書が公式仕様に反しているのに、黙って設計書どおり実装する
   → 動かないものを作る。あるいは本番で壊れる
❌ 設計書が間違っていると判断して、黙って自分の設計に差し替える
   → ユーザーの意図（外部要因・契約・既存資産）を踏み潰す
❌ 実装が設計書と違うのを見つけて、黙ってどちらかに寄せる
   → どちらが正だったのか誰も分からなくなる
❌ 「たぶん設計書の書き間違いだろう」と推測して進める
❌ 乖離を報告せず、実装完了後の報告に 1 行だけ書いて済ませる
   → 手戻りが最大化するタイミングで伝えることになる
```

## 4. 設計書に「書かれていないこと」の扱い

- **設計書に無い機能・テーブル・列・エンドポイントを勝手に足さない。** 必要だと考えるなら提案する。
- **設計書にある要素を勝手に削らない / 縮めない。** 実現困難なら §3 の手順で確認する。
- ただし、**本リポジトリのルールが要求する不変条件**（i18n / エラーハンドリング / ページング /
  RLS / テスト / 認証の必須導線 / 画像の transform / タップ標的 …）は、**設計書に書かれていなくても
  実装する**。これらは「追加機能」ではなく品質の下限であり、省くこと自体がルール違反である。
  ただし**設計書と真正面から矛盾する場合（例: 設計書が「OTP のみ」と明記）は §3 で確認**する。

| 11 | 公式推奨から逸脱するなら、**理由と根拠を残した**か |

## 6. 禁止パターン

```
❌ 設計書を受け取って、そのまま実装計画に落とす（一次情報を 1 つも読んでいない）
❌ 「このライブラリは知っている」で Context7 / 公式ドキュメントを飛ばす
❌ 該当 Skill があるのに起動せず、記憶ベースで設計する
❌ バージョンを確認せずにドキュメントを読む（別バージョンの API を設計に書く）
❌ ブログ記事・第三者の要約だけを根拠に技術選定する
❌ 「よくある設計パターン」を、調査せずにそのまま当てはめる
❌ テーブルだけ設計して RLS・index・ページングを後回しにする
❌ 乖離を見つけたのに、勝手に解消する / 黙って進める / 後で報告する
❌ 「意図的かミスか」を聞かずに、どちらかだと決めつける
❌ 調査したのに記録を残さない（次のセッションが同じ調査をやり直す）
```

## 8. 強制事項

このポリシーは**交渉の余地なし**。

- **一次情報を読まずに書かれた設計・実装計画は却下**し、調査からやり直す。
- **該当 Skill を起動せずに行った設計は却下**する（`.claude/rules/skills-first.md`）。
- **乖離を独断で解消した実装は却下**する。意図的かミスかの確認は**必ず行う**。
- 「開発者から指示が無かった」「設計書にそう書いてあった」は、いずれも理由にならない。
  設計書に従うことも、従わないことも、**確認を経ていなければ違反**である。
